# 记忆与追问 —— 设计文档

> 只定义设计，**不含实现**。写于 2026-08-07。
>
> 两件事放在一篇里，是因为它们是同一个问题的两面：**信息不全时怎么办**。
> 记忆负责"上次说过的不用再说"，追问负责"记忆也补不上的，开口问"。
>
> 相关：[系统架构](system-architecture.md) · [输出规格](output-spec.md)

---

## 0. 现状（读代码得到，非推测）

| 事实 | 位置 | 影响 |
| --- | --- | --- |
| **没有用户身份** | `api/deps.py::require_api_key` 是**共享**的 `APP_API_KEY`，不区分人 | 记忆无处安放，必须先有 profile 概念 |
| **没有任何持久化** | checkpointer 是 `MemorySaver`（进程内），缓存是内存 LRU | 进程一重启全丢 |
| checkpointer 按 trip 隔离 | `TripRunner._config` 用 `thread_id=trip_id` | 它记的是"这次规划到哪一步"，**不是**"这个人是谁" |
| 已有 `missing` / `questions` | `prompt_parser.TripDraft` | 追问的原料已经在了，缺的是**追问这个动作** |
| 已有中断机制 | `InterruptQuestion` + `interrupt()` | 图内追问可以直接复用，不用另造 |
| 缺字段就套默认值 | `prompt_parser.DEFAULTS` | 静默套默认值是当前"信息不全"的唯一处理方式 |

**当前的失败模式**：用户说「去成都玩几天」，系统默默按 1 位成人、经济舱、标准节奏、公共交通规划完，
用户拿到行程才发现全不对。它没说错，但它**没问**。

## 1. 记忆分三层，别混为一谈

| 层 | 记什么 | 活多久 | 存哪 | 现状 |
| --- | --- | --- | --- | --- |
| **L1 会话** | 这次规划到哪一步、挂起了什么问题 | 一次规划 | checkpointer | ✅ 已有 |
| **L2 偏好** | 这个人惯常怎么出行 | 长期 | 需要新建 | ❌ 无 |
| **L3 履历** | 这个人去过哪儿 | 长期 | 需要新建 | ❌ 无 |

L1 已经能用，本文档只设计 **L2 / L3**。

### 为什么要分开

L2 是**声明**（"我一般坐经济舱"），L3 是**事实**（"我去年去过西湖"）。
两者的信任级别不同：L2 可以直接拿来填参数，L3 只能用来降权，不能拿来做决定——
"去过"不等于"不想再去"（西湖去十次也正常，兵马俑一次就够了）。混在一起会得出
"你去过成都，所以不给你推荐成都的景点"这种蠢结论。

---

## 2. L2 偏好记忆

### 记哪些字段

只记 **`TripRequest` 里用户会重复表达、且跨行程稳定** 的字段：

| 字段 | 记 | 理由 |
| --- | --- | --- |
| `departure_city` | ✅ | 最稳定——一个人常年从同一个城市出发 |
| `travel_class` | ✅ | 舱位偏好几乎不变 |
| `pace` | ✅ | 节奏是性格，不是行程属性 |
| `transport` | ✅ | 会不会开车、愿不愿挤地铁，长期稳定 |
| `adults` / `children` / `children_ages` | ✅ | 家庭结构变化慢；**儿童年龄要按日期推进**，不能存死数字 |
| `budget_per_night` | ⚠️ 记区间不记数字 | 去三亚和去县城的预算不是一回事，只记「档位」 |
| `hotel_class` | ✅ | 同上 |
| `destination_city` | ❌ | 每次都不同，记了是噪音 |
| `outbound_date` / `return_date` | ❌ | 同上 |
| `must_visit` / `avoid` | ❌ | 强绑定目的地，属于 L3 的活 |

### 数据形状

```jsonc
{
  "profile_id": "usr_...",
  "updated_at": "2026-08-07T10:00:00+08:00",
  "preferences": {
    "departure_city": { "value": "PEK", "confidence": 0.9, "samples": 7,
                        "last_seen": "2026-08-07" },
    "pace":           { "value": "relaxed", "confidence": 0.6, "samples": 3,
                        "last_seen": "2026-07-01" }
  }
}
```

**每条偏好都带 `confidence` 和 `samples`**，不能只存一个裸值：

- 说过一次和说过七次，可信度天差地别；
- 低置信度的偏好只能拿来**建议**（"上次你是从北京走的，这次也一样吗？"），
  高置信度的才能**直接填**（并在 `origin` 里标明来自记忆）；
- 有了 `samples` 才能算出改变——一个人换了城市，第 1 次是异常，第 3 次是搬家。

### 怎么更新

**只在规划成功结束时写入**（`status == "done"`），不在解析阶段写。
解析出来的值可能被用户在中断点改掉，以最终生效的 `TripRequest` 为准。

置信度用简单的指数滑动，新观测权重 0.3：

```
命中：confidence ← confidence + 0.3 × (1 − confidence)
未命中（用户这次给了别的值）：confidence ← confidence × 0.7，samples 重置为 1，value 换新
```

不用复杂的贝叶斯——数据量太小（一个人一年规划十几次），复杂模型没有收益。

### 怎么用

在 `prompt_parser.resolve()` 里，**填默认值之前先查记忆**，`DraftField.origin` 加一个新值：

```
prompt   用户这次说的        ← 最高优先级
memory   从记忆里取的        ← 新增
derived  由其它字段推算的
default  系统默认值          ← 最低优先级
```

用户必须一眼看出哪些是记忆填的：

```
出发地    北京        [记忆]  你最近 7 次都从这儿出发
节奏      悠闲        [记忆]  上次你选的（置信度不高，可以改）
舱位      经济舱      [默认]  未提及，用默认值
```

⚠️ **记忆只填空，绝不覆盖**。用户这次说了什么就是什么，哪怕和记忆冲突——
冲突本身是有价值的信号（去更新记忆），不是需要"纠正"的错误。

## 3. L3 履历记忆

### 记什么

只记**规划完成后的最终行程**里出现过的：目的地城市、景点 `poi_id` + 名称 + 日期。
不记候选、不记备选——没去成的不算去过。

```jsonc
{
  "profile_id": "usr_...",
  "trips": [
    { "trip_id": "trp_...", "city": "成都市", "adcode": "510100",
      "dates": ["2026-09-10", "2026-09-14"],
      "attractions": [{ "poi_id": "B001...", "name": "都江堰景区" }] }
  ]
}
```

### 怎么用

**只做降权，不做过滤。** 在 `score_attractions` 里加一个衰减项：

```
去过 且 ≤ 6 个月：分数 × 0.5
去过 且 ≤ 2 年：  分数 × 0.8
更早 或 没去过：   不变
```

并且**必去景点豁免**——用户点名要去，去过一百次也照排。

⚠️ **绝不硬过滤。** 去过西湖不代表不想再去；而系统单方面把它从候选里删掉，
用户连"为什么没有西湖"都无从知道。降权 + 一句说明（"你 2026-03 去过，已降低推荐权重"）
才是对的。

## 4. 追问：信息不全时开口问

### 什么算"不全"

分两级，**只有第一级才值得打断用户**：

| 级别 | 判据 | 处理 |
| --- | --- | --- |
| **阻断** | `TripDraft.missing` 非空——出发地/目的地/日期缺任何一个 | 必须问，问不到就不能规划 |
| **可选** | 关键字段全靠 `default` 兜底（人数、节奏、预算…） | **问一次，可跳过** |
| 无 | 全部来自 `prompt` 或高置信度 `memory` | 不问，直接跑 |

### 「可选」这一级为什么值得做

现在这类信息一律静默套默认值。用户说「去成都玩几天」，系统按 1 人、标准节奏、
不限预算规划完——**它没说错，但它没问**。而这几个字段恰恰最影响结果：
人数决定机票钱，预算决定酒店档次，节奏决定一天排几个景点。

但也**不能变成查户口**。规则：

1. 最多问**一轮**，一次把该问的都列出来，不要挤牙膏；
2. 每个问题都必须能**跳过**（沿用现有的 `default` 机制）；
3. 记忆已经填上的**不问**——这正是记忆的价值所在；
4. 只问影响大的：人数、预算、节奏。舱位/市内交通的默认值足够安全，不问。

### 问题长什么样

复用现成的 `InterruptQuestion`，新增一种 `kind`：

```jsonc
{
  "id": "intake.clarify",
  "kind": "form",                       // 新增：一次收多个字段
  "title": "还有几件事想确认一下，也可以直接跳过",
  "fields": [
    { "key": "adults", "label": "几个人出行", "kind": "single_choice",
      "options": ["1", "2", "3", "4+"], "default": "1",
      "hint": "影响机票总价" },
    { "key": "budget_per_night", "label": "每晚住宿预算", "kind": "single_choice",
      "options": ["300 以内", "300-600", "600-1000", "1000 以上", "不限"],
      "default": "不限" },
    { "key": "pace", "label": "行程节奏", "kind": "single_choice",
      "options": ["悠闲", "标准", "紧凑"], "default": "标准" }
  ],
  "skippable": true,
  "expires_at": "..."
}
```

现有的 `QuestionKind` 只有 `single_choice` / `multi_choice` / `confirm`，
一次只能问一个字段。`form` 是新增的——三个问题分三次中断，用户要点三轮，
体验比一次问完差得多。

### 放在哪一步

**在 `intake` 之后、`resolve_city` 之前**，理由：

- 早于任何花额度的调用（机场补全是第一个烧 SerpAPI 的动作）；
- `intake` 已经校验完日期，此时缺什么是确定的；
- 用户改了人数/预算，后面的机票和酒店查询才用得上。

阻断级的缺失（没有目的地）比这更早——在 `POST /trips/parse` 就该返回
`missing` 让前端先补齐，根本不该走到创建行程。

### 超时怎么办

沿用现有纪律：**每个问题都必须有 `default`**，超时（`INTERRUPT_TIMEOUT_S`）
由清扫任务按默认值放行，并记 `ANSWER_TIMED_OUT`。追问不能成为新的卡死点。

## 5. 身份：绕不开的前置问题

**没有身份就没有记忆。** 当前 `APP_API_KEY` 是共享的，所有人共用一个 key。

三个选项：

| 方案 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| **A. 客户端自带 ID** | 请求头 `X-Profile-Id`，前端在 localStorage 生成 UUID | 换设备/清缓存就丢；任何人都能冒充别人的 id | 单机自用、demo |
| **B. 每人一个 API Key** | `APP_API_KEY` 从单值改成映射 `key → profile_id` | 要管理 key 的发放与吊销 | 小团队 |
| **C. 真正的登录** | OAuth / 账号密码 + 会话 | 一整套用户体系 | 面向公众 |

**建议先做 A**，并在文档里写清它不是安全边界：`X-Profile-Id` 只是"哪一份记忆"，
不承担鉴权（鉴权仍由 `X-API-Key` 负责）。B 是自然的下一步，C 等到真有多用户时再说。

⚠️ **A 方案下不要往记忆里写任何敏感信息**——profile_id 可猜，记忆内容等于半公开。
偏好（出发城市、节奏）无所谓，但绝不能存姓名、证件、支付信息。

## 6. 存储

记忆是**长期**数据，不能跟 checkpointer 一样放内存。

| 阶段 | 存储 | 理由 |
| --- | --- | --- |
| 第一步 | **SQLite 单文件**（`data/memory.db`） | 零运维，够用到几千个 profile；`--workers 1` 的现状下无并发问题 |
| 上多副本时 | Postgres | 和 checkpointer 一起迁（架构文档 §4.4 已埋了这个伏笔） |

两张表：`profiles`（L2 偏好，一行一个 profile，JSON 列）、`trip_history`（L3 履历，一行一次行程）。
不做 ORM——两张表、五个查询，直接 SQL 更清楚。

### 必须有的口子

- **导出**：`GET /api/v1/profile/me` 返回记住的全部内容。用户有权知道系统记了什么。
- **删除**：`DELETE /api/v1/profile/me` 清空。这不是可选项。
- **单条纠正**：`PATCH /api/v1/profile/me` 改掉某条偏好。比如换了城市，不该等三次采样才生效。

## 7. 影响面

| 改动 | 位置 | 性质 |
| --- | --- | --- |
| profile 身份 | `api/deps.py` 新增 `get_profile_id` | 新增，不影响现有路径 |
| 存储层 | 新建 `app/store/`（SQLite + 两张表） | 全新模块 |
| L2 读 | `prompt_parser.resolve()` 加 `memory=` 参数 | 纯增量，不传就是现在的行为 |
| L2 写 | `TripService` 在 `status == "done"` 时落盘 | 新增，失败不能影响行程 |
| L3 用 | `attraction_agent.score_attractions()` 加衰减项 | 要动打分，得补测试 |
| 追问 | 新节点 `clarify` + `QuestionKind` 加 `form` | 动图结构，要补 e2e |
| 三个 profile 接口 | `api/v1/routes_profile.py` | 新增路由 |

**建议顺序**：身份 → 存储 → L2 读写 → 追问 → L3。
每一步都能单独上线，L3 最后做（它要动打分，风险最高，收益最小）。

## 8. 明确不做的

- **不做跨用户的协同过滤**（"和你相似的人还去了…"）。数据量不够，且一上来就把
  单人偏好问题变成了推荐系统问题。
- **不用 LLM 管记忆**。偏好是结构化的几个字段，用规则读写清清楚楚；
  塞给模型只会引入不确定性和额外延迟。这和"日期一律由代码算"是同一条纪律。
- **不记自由文本**。只记 `TripRequest` 的枚举与数值字段。存一句"用户喜欢安静的地方"
  之后没有任何代码能可靠地消费它。
- **不做自动学习"讨厌什么"**。用户跳过一个景点的原因太多（时间不够、当天下雨、
  单纯没排上），据此推断厌恶几乎必错。`avoid` 只认用户明说的。
