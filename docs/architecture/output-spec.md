# 输出规格 v2

> 本文档**只定义输出应该长什么样**，不含实现。写于 2026-08-06，对应五条修改要求。
> 现状部分的证据均为当日实跑结果，不是推测。
>
> 相关：[系统架构](system-architecture.md) · 现有输出示例见 [README](../../README.md)

---

## 0. 总览：一份行程输出包含什么

```
① 航班      往返总价 · 去程航段 · 返程航段
② 酒店      候选列表（≥8 家）· 每家含地理位置
③ 逐日行程  景点游玩顺序 + 点到点的通勤时长（不含具体路线）
④ 备选      时间没排开的景点——用户点名的景点绝不出现在这里
⑤ 费用      机票 + 酒店，不含市内交通
```

已经定稿、本次不变的两条（见提交历史）：

- 景点**只给顺序，不给钟点**。排期内部照算精确时刻（要卡营业时间和返程窗口），
  但印出来的 `09:20-11:20` 精确得像承诺，路上一堵就全错位。
- **不显示门票**。高德极少返回 `business.cost`，多数景点只能印「门票?」，纯噪音。

## 1. 机场检索：先定位城市，再取该城市的机场

### 现状（实测）

```
$ resolve_airports("上海")   → 7 个
   PVG  上海浦东国际机场        ← 对
   SHA  上海虹桥国际机场        ← 对
   NUE  纽伦堡机场              ← 德国
   ZAQ  Nuremberg Hbf          ← 德国，还是火车站
   FRA  法兰克福机场            ← 德国
   HHN  Hahn Airport           ← 德国
   ZRB  Frankfurt Hbf          ← 德国，火车站

$ resolve_airports("北京")   → 11 个
   PEK / PKX 之后跟着 ORD（芝加哥奥黑尔）、STL、MDW、PIA、FAR、MOT、BIS、GFK、DVL
```

### 根因

Autocomplete 返回的是**多个城市建议**，每个建议自带机场列表：

```jsonc
[
  {"name": "中国上海市",     "id": "/m/06wjf",   "type": "city",
   "airports": [{"id": "PVG", "city_id": "/m/06wjf"}, {"id": "SHA", "city_id": "/m/06wjf"}]},
  {"name": "上海市",         "id": "/m/06wjf",   "airports": []},
  {"name": "德国上海德",     "id": "/m/02q0yzg", "airports": [NUE, ZAQ]},   // 子串命中
  {"name": "德国上海因巴赫", "id": "/m/02z2zgt", "airports": [FRA, HHN, ZRB]}
]
```

「上海德」「上海因巴赫」是德国地名的中译，恰好**包含「上海」二字**。
当前实现把所有建议的机场拍平合并，于是德国机场混了进来。

### 期望输出

**只保留与首个建议同属一个城市的机场。** 判定用 `airport.city_id == suggestion.id`，
不要用名字做模糊匹配——`city_id` 是 Google 的实体 ID，等值比较即可。

```
上海 → 2 个
   PVG  上海浦东国际机场   距市中心 20 英里
   SHA  上海虹桥国际机场   距市中心 8 英里

北京 → 2 个
   PEK  北京首都国际机场
   PKX  北京大兴国际机场
```

### 规则

| # | 规则 |
| --- | --- |
| 1.1 | 取 `suggestions` 中**第一个带机场的**建议作为锚点城市 |
| 1.2 | 只收 `city_id` 等于锚点 `id` 的机场；其余建议整条丢弃 |
| 1.3 | 目的地限中国大陆（D1），锚点城市不在中国大陆时报 `DESTINATION_UNSUPPORTED`，而不是静默返回外国机场 |
| 1.4 | 火车站（`ZAQ`/`ZRB` 这类 Google 混进来的地面站点）不进候选 |
| 1.5 | 过滤后一个不剩时，**不要**退回未过滤的全集——报 `CITY_NOT_FOUND` 让用户换个说法 |
| 1.6 | 候选按「距市中心距离」升序，`distance` 字段直接展示给用户 |

### 验收

- `上海` → 恰好 `{PVG, SHA}`；`北京` → 恰好 `{PEK, PKX}`
- `成都` → 恰好 `{CTU, TFU}`
- 任何城市的候选里不出现非中国大陆机场
- 给用户的选择题选项 ≤ 4 个（超过就不是"选择"而是"翻页"了）

## 2. 酒店：候选更多，且每家都要有地理位置

### 现状

`TOP_N = 3`，重排后只留 3 家。展示只有名字 + 价格 + 评分 + 通勤分钟：

```
🏨 酒店　Merica Hotel -Chengdu Chunxi Road
    价格暂无 · 4.2 分 · 到景点集中区 45 分钟
```

`HotelCandidate` 里其实已经有 `location`（GeoPoint，GCJ-02）和 `address`，**没有展示**。

### 期望输出

候选 **8 家**，列表形态，每家带地址和相对位置：

```
🏨 酒店候选（8 家，已按综合评分排序）

  ★ 1. 全季酒店成都春熙路店                     ¥520/晚 · 4.6分 · 4星
       成都市锦江区红星路三段1号                 距景点集中区 12 分钟
    2. 桔子水晶成都太古里酒店                    ¥680/晚 · 4.7分 · 4星
       成都市锦江区大慈寺路8号                   距景点集中区 15 分钟
    3. 亚朵酒店成都天府广场店                    ¥450/晚 · 4.5分 · 4星
       成都市青羊区人民南路一段86号              距景点集中区 18 分钟
    …
  ★ = 已自动选中
```

### 规则

| # | 规则 |
| --- | --- |
| 2.1 | 候选数 `TOP_N` 从 3 提到 **8** |
| 2.2 | 每家必须给出 `address`（文字地址）。缺失时降级显示所在区县，仍缺则标「地址暂缺」 |
| 2.3 | 每家给出 `location`，**坐标系按来源原样保留**（SerpAPI = WGS-84，高德降级 = GCJ-02），`GeoPoint.crs` 自带标注。API 返回供前端打点；终端输出不印经纬度 |
| 2.4 | 每家给出「距景点集中区 N 分钟」，即已有的 `commute_to_centroid_min` |
| 2.5 | 价格缺失时显示「价格暂无」，**不要**显示 ¥0 |
| 2.6 | 广告位（`is_ad`）不过滤，但要打「广告」标签 |
| 2.7 | 候选变多不等于中断问题的选项变多——询问用户时仍只列**前 4 家** |

### 注意

`TOP_N` 提到 8 只影响重排后的保留数量，**不增加 SerpAPI 调用**（一次搜索本来就返回更多，
只是被截断了）。但 `commute_to_centroid_min` 是逐家算的，8 家意味着高德调用从 3 次变 8 次——
高德免费额度 5000/日，可以接受。

### 验收

- 正常城市返回 8 家；不足 5 家时给出 `HOTEL_FEW_CANDIDATES` 警告
- 每家都有非空地址或明确的「地址暂缺」
- `location.crs` 非空且与来源一致——**不要**在入库时统一转坐标系，
  裸浮点数传来传去迟早会串（架构 §9.1），转换只在进高德接口那一步做

## 3. 通勤：按距离给对应方式的时长，不给路线

### 现状

给了具体路线，正是不想要的那部分：

```
      ↓ transit 62 分钟 · 地铁5号线 → 地铁3号线（步行 1671 米）
      ↓ transit 36 分钟 · 地铁4号线 → 地铁5号线（步行 1292 米）
      ↓ walking 13 分钟 · 步行 997 米
```

`RouteLeg.detail` 就是这段文字，`RouteLeg.mode` 只有一个值。

### 期望输出

**以 2 km 为界**：2 km 以内**多给一个**步行选项，2 km 以外只给驾车和公交。
三种方式都**不带线路名**：

```
      ↓ 步行 14 分钟 / 公交 11 分钟 / 驾车 6 分钟      ← 1.2 km，走得动
      ↓ 公交 36 分钟 / 驾车 18 分钟                    ← 5.4 km，别走了
      ↓ 公交 62 分钟 / 驾车 35 分钟                    ← 21 km
```

### 规则

| # | 规则 |
| --- | --- |
| 3.1 | **近**（直线距离 < 2 km）：给 `步行 / 公交 / 驾车` 三个选项 |
| 3.2 | **远**（≥ 2 km）：只给 `公交 / 驾车`，不给步行 |
| 3.3 | 一律**不输出** `RouteLeg.detail`（线路名、换乘次数、步行米数） |
| 3.4 | 不输出 `distance_m`。用户要的是"多久"，不是"多远" |
| 3.5 | 某一种方式查不到时略过它，不要显示「约 N 分钟」占位；三种全查不到才降级为估算 |
| 3.6 | `detail` 字段在 API 里保留，只是终端输出不印——前端要画路线时还用得上 |
| 3.7 | 排期算时间**只用一种**方式（用户选的 `transport`），多出来的选项纯属展示 |

> ⚠️ 3.7 是关键：给三个时长不代表行程可以按任一种走。时刻表按用户选定的
> `transport` 推算，另外两个是"你也可以这样走"的参考。

### 关于「地铁」

高德的公交路线规划（`direction_transit`）返回的是**地铁 + 公交的综合方案**，
没有"只要地铁"的参数。实测成都的段落里既有「地铁3号线」也有「63路」。
所以标签用「公交」而不是「地铁」——写"地铁 36 分钟"而实际含两段公交，是撒谎。

### 阈值取 2 km 的理由

2 km 按成人步行速度约 25 分钟，是"愿意走"的上限。再远就该坐车了。

### 代价

| 段类型 | 现在 | 改后 |
| --- | --- | --- |
| < 2 km | 1 次（用户选的方式） | 3 次 |
| ≥ 2 km | 1 次 | 2 次 |

一次 5 天行程约 20 段，粗算 45 次高德调用（现在 20 次）。免费额度 5000/日，可以接受。
缓存 TTL 15 分钟内重复规划不再扣。

### 验收

- 输出中不出现「地铁3号线」「63路」「换乘」「米」等线路细节
- 1.2 km 的段有步行选项，5 km 的段没有
- 三种时长都指同一对起讫点，不会张冠李戴

## 4. 用户点名的景点必须排进去

### 现状

`split_day_trips()` 里必去景点确实豁免了"当日往返半径"过滤（[route_planner.py:103](../../app/agents/route_planner.py#L103)），
**但排期阶段没有豁免**。第二轮实测精修时，超出时间窗的景点会被丢进 `unscheduled`，
必去与否一视同仁。实跑中出现过：

```
💤 时间没排开的备选：麓湖水城景区、黄龙溪古镇、…、都江堰景区、青城山景区
⚠️  ATTRACTIONS_UNSCHEDULED: 有 11 个景点没能排进时间窗，已作为备选列出
```

如果用户 `--must 都江堰`，它照样会出现在备选里——这就是"我说了要去，你没给我安排"。

### 期望输出

必去景点**保证进入 `days`**，代价由别的景点承担：

```
🗓  第 3 天　2026-09-07
    📍 1. 都江堰景区          ← 用户点名，优先占位
      ↓ 公交 95 分钟 / 驾车 62 分钟
    📍 2. 青城山景区

💤 时间没排开的备选：文殊院、成都动物园、东郊记忆
⚠️  MUST_VISIT_CROWDED_OUT: 为安排「都江堰景区」，3 个候选景点移入备选
```

### 规则

| # | 规则 |
| --- | --- |
| 4.1 | 必去景点在分天、排序、排期**三个阶段**都优先 |
| 4.2 | 排期时先给必去景点占位，剩余时间窗再塞普通景点 |
| 4.3 | 必去景点**不得**进入 `unscheduled` |
| 4.4 | 挤掉了普通景点时给 `MUST_VISIT_CROWDED_OUT` 警告，说明代价 |
| 4.5 | 必去景点数量本身就超过总时间窗时，按用户给出的顺序尽量排，排不下的报 `MUST_VISIT_IMPOSSIBLE` 并明确告知——这是唯一可以不排的情形，且必须显式告警 |
| 4.6 | 用户报的名字在景点池里找不到时，报 `MUST_VISIT_NOT_FOUND` 并列出最接近的几个，**不要静默忽略** |

### 验收

- `--must 都江堰` 时，都江堰出现在某一天的 `days` 里，且不在 `unscheduled`
- 必去景点远到需要整天时，那一天只排它（外加通勤）
- `--must 不存在的地方` 时有明确告警，不是悄悄没了

### 4.x 实现方案（代码怎么动）

先说清**为什么现在会掉**——三个环节，掉在第二和第三个：

| 环节 | 函数 | 必去优先？ |
| --- | --- | --- |
| 分天 | `split_day_trips` / `assign_days` | ✅ 已豁免半径过滤，桶内也按 `(must_visit, score)` 降序 |
| 排序 | `order_within_day` → `_tsp_order` | ❌ **纯按地理位置重排，把上一步的优先级抹掉了** |
| 排期 | `schedule_day` + `build_itinerary` 第二轮 | ❌ 塞不下就丢，不看 `must_visit` |

`schedule_day` 第 278 行是重灾区：

```python
fitted = fit_visit(attraction, arrive, window.day, window.end)
if fitted is None:
    leftover.extend(ordered[index:])   # ← 这站去不了，后面全丢
    break
```

TSP 把必去景点排到了当天第 4 位，前 3 个把时间窗吃光，第 4 位就整批进了 `leftover`。

#### 方案 A：回补循环（小改，建议先做）

不动 `schedule_day` 的结构，在它外面加一层修复：

```
planned, leftover = schedule_day(ordered, window, hotel)
while 必去景点 in leftover 且 planned 里还有普通景点:
    从 planned 里踢掉分数最低的普通景点
    用剩下的成员重新 order_within_day + schedule_day
```

- **改动**：`route_planner.py` 新增一个 `_repair_must_visit()`，`build_itinerary` 两轮各调一次
- **优点**：`schedule_day` / `_tsp_order` 一行不动，风险低
- **缺点**：最坏情况下要重跑 N 次排期。但每天最多 6 个点，N ≤ 6，纯计算不花额度
- **盲区**：必去景点在**本天**怎么也塞不下时（比如都江堰要一整天，而这天已经被航班切掉半天），
  方案 A 只能放弃。需要配合下面的跨天调度

#### 方案 B：两阶段排期（正解，改动大）

把「先占位再填充」写进算法本身：

```
1. must = [必去]，rest = [其余]
2. planned = schedule_day(order_within_day(must), window, hotel)     # 必去先占满
3. for spot in rest（按分数降序）:
       找 planned 中"插入后通勤增量最小"的位置，试着插入
       插得进就留下，插不进就进 leftover
```

- **改动**：`schedule_day` 拆成 `schedule_fixed()` + `insert_optional()`，`build_itinerary` 两轮都改
- **优点**：必去景点**结构性地**不可能被挤掉；插入启发式还能顺带改善总通勤
- **缺点**：改的是全项目最复杂的函数，现有 `test_route_planner.py` 大概率要重写一批
- 这是最终该走的路，但不该和其它四条改动混在一个批次里

#### 跨天调度（两个方案都需要）

必去景点在分配到的那天塞不下时，要允许它换一天：

```
for spot in 仍在 leftover 的必去景点:
    找一个「同方向且有余量」的日子，移过去重排
    所有日子都塞不下 → MUST_VISIT_IMPOSSIBLE
```

「同方向」用现有的 `cluster_by_bearing` 判据，避免为了塞进去而让某天来回横穿城市。

#### `MUST_VISIT_NOT_FOUND` 单独改一处

在 [attraction_agent.py:127](../../app/agents/attraction_agent.py#L127)：

```python
if not results:
    log.warning("必去景点没搜到", ...)
    continue          # ← 只写日志，用户完全不知道
```

改成往 state 里塞一条 `PlanWarning`，并带上同城最接近的 3 个候选名。
这条**和排期完全无关**，可以单独先做，5 行代码。

#### 建议的落地顺序

1. `MUST_VISIT_NOT_FOUND`（独立，5 行）
2. 方案 A + 跨天调度（覆盖绝大多数场景）
3. 方案 B（等其它四条稳定后单独一轮）

## 5. 费用只算机票和酒店

### 现状

```
📊 合计　通勤 526 分钟 · 交通 ¥39
```

`Itinerary.totals()` 返回 `commute_min` / `transport_cost_cny` / `ticket_cost_cny`，
机票和酒店的钱**根本没进这个合计**，反而算了最不重要的市内交通。

### 期望输出

```
💰 预估花费　机票 ¥2300 + 住宿 ¥2080（4 晚 × ¥520） = ¥4380
📊 行程强度　全程通勤 526 分钟
```

### 规则

| # | 规则 |
| --- | --- |
| 5.1 | 费用合计 = 机票总价（往返，全部乘客）+ 酒店总价（总房价，非每晚价） |
| 5.2 | **不计入**市内交通费。金额小、误差大，混进总价反而降低可信度 |
| 5.3 | **不计入**门票（数据缺失，见第 0 节） |
| 5.4 | 分项列出，不要只给一个总数——用户要知道钱花在哪 |
| 5.5 | 任一分项缺失时明说缺哪项，**不要**当 0 算：`机票 ¥2300 + 住宿（价格暂无）` |
| 5.6 | `commute_min` 从"费用"里挪出去，改称"行程强度"。它是时间不是钱 |
| 5.7 | `transport_cost_cny` 在 API 里保留，只是不进费用合计与终端输出 |

### 验收

- 合计恒等于机票 + 酒店，手算可验
- 酒店价格缺失时合计不显示为「¥2300」，而是标明住宿未知
- 多人行程时机票价按实际乘客数（SerpAPI 返回的就是总价，不要再乘）
